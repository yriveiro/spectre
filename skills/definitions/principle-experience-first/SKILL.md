# Principle: Experience First

Experience first is a choice between two costs. One is paid once, by you, while
you build. The other is paid by every user, every time, for as long as the thing
exists: a setting that saved an afternoon in design charges every user a decision
forever. The principle says the second cost wins, and that paying it well means
shipping fewer things. It exists because the second cost is invisible at the
moment you spend the first one, and the first one is the only one you can feel.
It is adjacent to `principle-laziness-protocol`, which owns the decision to refuse
the addition while it is still hypothetical; this leaf owns the surface that
survives the refusal, which is the part nobody measures.

There is no falsifiable test here, and no command reports that an experience is
right. Saying so plainly is the honest position rather than a gap to paper over,
so what follows is a moment and a set of acts. The moment is the point where
convenience and delight conflict and only one can win: you are about to add one
more flag, one more option, one more mode, or you are spreading polish evenly
across a wide surface instead of concentrating it where the time actually goes.
Either temptation is the signal. A principle with no test is not a principle
without a discipline. It is one whose discipline is a judgement made at a named
point, which is harder to skip and easier to fake, and the moves below are what it
consists of.

Without this, products grow by addition and shrink by abandonment. Each release
adds an option nobody asked to choose between, each screen carries one more
control that made a review shorter, and the whole reads as competent and
forgettable. Half-polished is worse than absent, because absent sets no
expectation: a surface that is eighty percent finished teaches users that nothing
here can be trusted, and that lesson transfers to the twenty percent you did
finish. Users do not remember the ten things a tool does. They remember the one
thing it did that felt considered.

## The moves

**Stop at the moment and name it.** Convenience and delight in conflict is a
decision point, not a trade-off to average. Say which one you are giving up, and
to whom: this flag is cheap for me and costs the user a decision on every run. A
trade-off nobody named is a trade-off nobody is accountable for.

**List what disappears before what gets added.** A request can usually be met by
removing a mode, merging two, or narrowing a scope. Write the smaller surface
first, because the addition is the only list on the page and it makes itself look
necessary.

**Name which user, doing what, feels the difference.** Everyone is not a
beneficiary, and power users is not a moment. If the person who feels the
improvement cannot be described in a sentence naming an action they were already
taking, the improvement is for you, and you are the reader.

**Read a request for the problem under it.** Most requests for a flag are a
complaint about the default: the thing is slow, surprising, or missing for one
case. Fix the default and the flag has no reason to exist. A setting that covers
one case reachable by a one-line edit has cost more than it saved.

**Ship fewer things, finished.** A narrow surface where every edge has been
considered beats a wide one where each part is adequate, and adequate is not
remembered. Finished is concrete: the empty state, the error, the second run, the
value at the limit, the person who signed up for none of this.

**Spend polish where the time goes, not evenly.** Concentrate the care on the
path most people take and let the rest be plain. Polish spread evenly across a
wide surface costs the same and is felt nowhere, which is the definition of a
transfer.

**Delete the half-finished half rather than shipping it greyed.** A feature
visible but unfinished is worse than an absent one, because it advertises
attention you did not pay. Absence sets no expectation.

**Treat every option as a charge on every user.** The afternoon a setting saved
you is a one-time cost against a permanent one. Forty settings have asked forty
questions and answered none of them, and the person paying is the one who never
opens the menu.

**Make the default the product, and design it as if the options did not exist.**
The default is what most people get. If the thing only works once the user has
chosen correctly, the default is a bug report waiting for a name. An option earns
its place when the default genuinely fails, not when you are unwilling to decide.

**Ask what a new user meets in the first minute.** That is where the experience is
decided and it is the only part of the surface every user sees. A first run that
requires a setting chosen is a design that has not started.

**Let the memory be the check.** Users do not retain a feature list, they retain
one moment. Ask which one you can name about your own product. If the answer is it
is fast or it does everything, that is a list, and a list is not a memory.

**Name what you refused.** A refusal nobody can see reads as an absence, and the
person who asked concludes the work was cut short. Say what the thing deliberately
does not do, in the release note, the readme, or the reply, and say why. The
refusal is the craft, and it only counts if it is visible.

**Keep the surface stable, and take removals out of the user's hands carefully.**
A product that grows by addition and shrinks by abandonment feels broken in a way
it is not. A removed feature is attention a user already paid to give, so a
surface that shrinks at design time is cheaper than one that shrinks after
launch.

## What this principle is not

- **Not a licence to ship an unfinished thing.** Refusing an addition is not the
  same as shipping a partial one. An honest gap the user can see beats a polished
  surface over a floor that does not hold, and whether the floor holds is
  `principle-verification`'s to answer.
- **Not a demand for taste.** Delight is still somebody's preference, and yours is
  not privileged. The beneficiary is named in a sentence, and if the sentence
  names you, the polish is for you.
- **Not minimalism as a look.** A stripped interface that hides the affordance is
  not restraint, it is a user guessing. Restraint is about decisions, not about
  removing words, and a surface with one button and no way to undo is a worse
  product than a wide one that is honest about itself.
