Two fixes built on the same premise failed the same gate. The premise is the bug. Stop writing fixes and attack the sentence they share.

A failed fix asks for another fix. That is the trap. Each attempt feels like progress while it is the same bet placed again, and the gate keeps collecting the same answer. You spend the afternoon tuning parameters of an idea that already lost twice. Worse, every attempt raises the price of quitting: with three fixes on the board, abandoning the premise means admitting three failures instead of one. So you write fix four, and the premise survives on sunk cost alone.

**Write the premise down in one sentence.** If it cannot be written plainly, that is already information. A belief you cannot state is not a foundation; it is a mood.

**Count the failures against it.** Two or more fixes sharing one premise and failing the same gate is the threshold. Keep the count where you can see it, because memory forgives and the count does not.

**Do not start the next fix first.** That is the test. Before another fix exists, the premise must be negated, replaced, or proved from scratch. Ask the question: what would I try if this sentence were false? If the answer is nothing, you have not attacked it yet.

Reach for this the moment the second fix fails where the first one did. A single failure is noise, and noise belongs to principle-verification: reproduce it, check the claim, then diagnose. A decision with no precedent at all belongs to principle-exhaust-the-design-space, where you build competing options before committing instead of after failing. This skill owns the middle case: repeated failure under one shared belief.

A premise that survives the attack earns its fixes. One that does not was never load-bearing. Write it, count against it, and let the count decide.
